Yes — 100% possible. What you saw is a transition table (a.k.a. delegate-based FSM): a list of  {from, to, condition}  rows where the condition is a lambda, and the whole machine reads like a spreadsheet. Odin's  proc  values are first-class, so lambdas work — and your codebase is actually the easiest case for it, because your conditions all read globals ( input ,  interact_target_found ,  main_actor ), which means the lambdas don't even need to capture anything.
Here's what it looks like mapped onto your real states and real conditions:
// odin
// ─────────────────────────────────────────────
// THE WHOLE MACHINE ON ONE PAGE
// rows are checked top→bottom, first match wins
// ─────────────────────────────────────────────
Actor_Transition :: struct {
	from, to: Actor_State,
	cond:     proc() -> bool,
}
 
actor_transitions := []Actor_Transition{
	//  from         to            when
	{.IDLE,     .WALK,     proc() -> bool { return input.move_dir != 0 }},
	{.IDLE,     .INTERACT, proc() -> bool { return input.wants_interact && interact_target_found }},
	{.WALK,     .INTERACT, proc() -> bool { return input.wants_interact && interact_target_found }},
	{.WALK,     .IDLE,     proc() -> bool { return input.move_dir == 0 }},
	{.INTERACT, .STAIR,    proc() -> bool { return interact_anim_done && stair_target_found }},
	{.INTERACT, .DIALOGUE, proc() -> bool { return interact_anim_done && dialogue_target_found }},
	{.INTERACT, .WALK,     proc() -> bool { return interact_anim_done && input.move_dir != 0 }},
	{.INTERACT, .IDLE,     proc() -> bool { return interact_anim_done }},
}
That's it. That's the whole "what can leave each state, and why" — no reading handler bodies to find out.
The runner is tiny:
// odin
set_state :: proc(actor: ^Actor, new: Actor_State) {
	if actor.state == new do return
	fmt.println(actor.name, "->", actor_state_strings[new])
	actor.state = new
}
 
transition_actor :: proc(actor: ^Actor) {
	for &t in actor_transitions {
		if t.from == actor.state && t.cond() {
			set_state(actor, t.to)
			return
		}
	}
}
And it plugs into your existing two-tier loop with almost no disruption — the  #partial switch es stay for behavior (fixed-step for IDLE/WALK, per-frame for INTERACT/DIALOGUE/STAIR), you just strip the  switch  blocks out of the handlers and call one scan:
// odin
update :: proc() {
	// ...interact targets as today...
	update_actor_events(main_actor)  // INTERACT/DIALOGUE/STAIR behavior, sets flags
	transition_actor(main_actor)     // ← one scan, first match wins
}
The flags  interact_anim_done ,  dialogue_target_found ,  stair_target_found  become package globals that  handle_interact  sets (it already computes exactly these locals — they just move up a level).
The honest caveats, since you're asking "is this good for me"
- Rows are guards, not actions. Dialogue advancing (SPACE → next line), stair walking, camera switching — those are side effects that stay in the  handle_*  procs. The table answers "can we leave X?" — it doesn't do anything. That's fine and matches the C# pattern, but DIALOGUE → IDLE won't fit cleanly as a row (it's "SPACE pressed AND dialogue ran out" — a side-effect-flavored condition). Keep that one as a  set_state(actor, .IDLE)  inside  handle_dialogue , or add a  dialogue_finished  flag if you want it in the table. Either is fine.
- Order = priority. Your current code has implicit priorities (WALK beats INTERACT in IDLE, STAIR beats DIALOGUE in INTERACT). The table makes that ordering visible — that's a feature. Add a  // rows checked top→bottom  comment so future-you doesn't reorder and break it.
- It surfaces your STAIR bug for free. Notice I wrote  interact_anim_done && stair_target_found  on the STAIR row — your current  walk_stairs_cond := is_stair  skips the  animation_ended  check every other condition has. In the table it's a one-character-sight fix that jumps out at you instead of hiding inside a handler.
- Zero capture, zero lifetime worries — in your case. Since  input ,  interact_target_found , etc. are package globals, the lambdas read globals directly — they're not closures, no captured-frame-lifetime footguns. If you ever write a lambda that closes over a local (e.g.  proc() -> bool { return anim_done } ), remember Odin closures capture by reference and the captured frame must outlive the closure — with a package-scope table that's a trap, so prefer globals or parameters.
-  proc  fields make the struct non-comparable — irrelevant here, just don't try  ==  on transitions.
